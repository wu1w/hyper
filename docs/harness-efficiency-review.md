# 长会话与开发效率检查（2026-09-06）

本次检查覆盖 agent 主循环、消息恢复、压缩与 Responses 请求、历史索引与召回、工具 schema、预执行与串并行调度、编译诊断、提示词、配置和现有基准。证据来自当前代码、本机已有会话的只读统计、离线回归测试及官方公开文档。没有运行 Cursor/Grok 同题在线 A/B，也没有把离线测试结果当成模型质量提升比例。

## 核心结论

工具名称对齐只能提供熟悉的接口，不能替代有效的上下文和工具语义。当前主要问题是：提前丢弃上下文、丢弃后缺少可达的原文入口、把合理的补充检索误判为重复，以及重复或无明确结果的编译检查。这些机制共同制造了“丢信息 → 补证据 → 被拦截 → 换参数再查”的循环。

这里的“跳数”必须分开计量：一次模型回复可以并行请求多个工具。不能把 292 个工具结果等同于 292 次串行模型请求。

## 真实日志证据

仅统计本机主会话，不把子代理工具累加到父会话。计数脚本不输出提示词、模型正文、工具内容和凭据。

- 会话 `7d739354…`：6 条用户消息，63 条已记录模型回复，292 个工具结果，5 次压缩。58 个工具结果以“相似 Grep 已执行”开头，7 个以“Grep 预算用完”开头；合计 65 个、占 22.26%。缓存命中占有缓存统计的输入 token 的 69.30%。
- 会话 `2b6c5da2…`：2 条用户消息，38 条模型回复，199 个工具结果，1 次压缩。21 个结果为 Grep 预算劝退，占 10.55%。可测输入缓存命中占比为 86.84%。
- 会话 `844f3714…`：1 条用户消息，24 条模型回复，134 个工具结果，没有压缩。7 个结果为 Grep 预算劝退，占 5.22%。

这些数字证明缓存和批量调用已经在工作；继续只优化 schema 字节或扩大并行，不能解决主要的信息缺口。劝退占比仅统计已知返回前缀，是无新检索证据结果的保守计数，不代表每次劝退都不合理，也不是修复后的提速估计。

复现：`python3 scripts/audit-session-efficiency.py --limit 3`。脚本支持 `--session-dir` 和 `--include-subagents`。缓存字段缺失不会当作零命中；模型回复数不包含未记录的 HTTP 重试。

## 已修复

### 1. 工具计数触发的提前有损压缩

旧 `should_compact_follow_up` 只要活跃历史有 8 个工具结果，就能在下一条用户消息开始时归档。即使内容只有约 1k token，也会触发。标称 500k 窗口并不能防止这条规则。

本地归档是规则抽取和截断，不是模型语义总结：归档正文上限 4000 字符；历史卡仅取最近 3 条结论、每条 280 字符；早期用户要求还有数量/长度限制。多轮连续项目的信息会逐渐落出这些切片。

修改后：普通工具数量不触发压缩；文本按 soft threshold 和 200k 输入阈值处理，保留截图的独立阈值。相对原先 120k 跟进压缩阈值，这会保留更多上下文，也可能增加单次请求输入；需要结合真实缓存和延迟评估，而不是无条件追求最短上下文。

### 2. 原文存着，模型却没有可用的召回接口

旧正式工具面不挂载 `recall`，压缩还会主动移除它；历史卡同时要求不要读取会话 JSONL。旧代码关于“Cursor 压缩只依赖摘要、不提供历史搜索”的断言没有事实依据。

修改后：`recall` 从 agent 会话开始固定挂载，压缩不再改变工具列表。支持关键词搜索、事件序号展开、完整 blob 读取；小事件搜索时直接带原文，减少“先找 ID，再展开”的额外模型往返。

历史卡现在优先根据当前问题检索本场已归档的用户消息和助手结论，再附近期摘要。中文采用连续双字片段和精确词匹配，补足 unicode61 对连续中文句子的检索缺陷。JSONL 保留为真源；索引缺失或检索不可用时可从原事件召回。隐藏注记、推理字段和召回自回声不作为新记忆。

这仍是词法检索，不能保证“继续上面的”这种没有可识别关键词的请求总能恢复全部隐含约束。

### 3. 以减少调用为名，拦截正确的证据请求

旧规则包括：Grep 相似性比较忽略完整调用参数；Search 显示了文件的一个函数，就阻止读取该文件较大范围；整文件读取标记不反映后续文件变化；Search 4 次、Grep 12 次后返回劝退。工具执行后还有第二遍折叠，会把已经得到的真实结果替换成劝退文本。

Grok（包括兼容端点上的 Grok 模型）现在跳过这些启发式拦截及结果替换，并同步取消对应的预执行抑制。用户明确禁止的工具、审批、计划模式、子代理权限、依赖操作顺序和相同参数循环终止仍然生效。原本针对其他模型的旧策略保留，未扩展本次行为变化范围。

### 4. 自动诊断重复运行、成功不可见、输出管道阻塞

原先每完成一次修改，就中止上一个异步诊断包装并再启动一个。底层使用 `spawn_blocking`，中止包装不会取消已经运行的编译进程，可能造成并发 cargo check 和构建锁竞争。

旧诊断成功返回 `None`；提示词又要求“缺少 diagnostics 就再检查”。此外，子进程退出前没有持续读取 stdout/stderr，输出达到管道容量会阻塞，最终触发 12 秒超时。退出码未保留，部分非正常退出还可能被误判为没有错误。

修改后：一批修改完成后检查一次最终状态；覆盖该批涉及的 Rust 包；成功与错误都回传明确诊断；同时排空 stdout/stderr 并保留退出状态。超时/缺工具不冒充通过。修复中文诊断按字节截断时的 UTF-8 panic。编译通过仍不等于测试通过。

### 5. 官方压缩与本地归档之间的状态错位

旧流程通常先本地丢信息，再判断是否调用官方压缩；另有“工具数 ≥8 就不调用官方压缩”的分支。发生过官方压缩后，再次本地压缩会更新 skip，却可能留下不包含新归档事件的旧 blob，导致发送时漏掉信息。

现在达到官方阈值时先发送实际上下文；连续官方压缩使用前一个 blob 加新增后缀；本地重写会同时清除旧 blob/skip。新 blob 在本地重写完成后安装，并绑定对应偏移。官方请求等待可被取消。

官方 blob 仍是进程内状态，跨进程恢复依赖 JSONL、本地归档和召回。跨重启持久化官方快照、模型切换时失效，以及压缩后按服务端真实 token 用量反馈预算，仍值得单独实现。

### 6. 提示词中的错误目标

旧默认文案要求：给了路径就 Write；审计只读代表性样本。它既可能诱导覆盖已有文件，也与完整检查的意图冲突。

现在明确先读已有文件、完成请求范围、延续用户约束，并在已有上下文不足时调用 recall。相关修改应批量完成后再验证。已识别的内置旧提示词会升级；用户自定义角色及项目规则保留。

## 为什么对不上 Cursor + Grok

Cursor 的公开设计强调按模型调优 harness，并在摘要不足时提供原始聊天历史的检索入口，而非仅模仿工具名称。[Agent 概览](https://cursor.com/docs/agent/overview)、[动态上下文发现](https://cursor.com/blog/dynamic-context-discovery)支持这一点。

本项目关于“工具 schema 必须与 Cursor 数量完全相同，所以不能放 recall”的取舍，牺牲了功能而没有带来已验证的质量收益。更合适的目标是：工具描述和行为一致、返回真实且足够的证据、原文可恢复、任务状态连续。

也不能把差距全部归于“没有向量库”。Cursor 的检索实现持续变化，2026 年 7 月官方工作人员已说明正在转向 grep 检索及本地 Instant Grep。[官方说明](https://forum.cursor.com/t/what-do-you-think-about-cursor-removing-the-codebase-indexing-settings/165899/10)。当前本机 `features.code_search=false` 确实关闭了项目自带的 FTS Search，但现有 Grep 本身是可用的，先修正确性比盲目增加另一个搜索工具更有证据支持。

xAI 官方要求把压缩结果作为后续请求的历史表示，再追加新消息；它不是一种能从已丢弃摘要中恢复原文的魔法。[Context Compaction](https://docs.x.ai/developers/advanced-api-usage/context-compaction)。

没有相同输入、相同模型版本/端点、相同 effort、相同任务验收的比较数据，不能断言 Cursor 的私有系统提示词、模型权重或服务优先级导致了多少差距。

## 剩余设计工作与验证边界

- 本机 `default_effort=auto` 映射为 xhigh，每个不必要的模型往返都承担高思考延迟。本次没有降低默认推理强度以掩盖信息问题。后续应单独对比 high/xhigh 的正确率与耗时。
- 当前本地摘要仍会截断约束。需要长期维护可追溯的任务状态：目标、最新约束、已修改文件、通过/失败的验证及剩余工作。检索负责展开证据，不能完全替代任务状态。
- 混合工具批次的并行策略仍较保守。应按读写依赖分组，不能直接把所有 Shell/Write 放入 join_all。该优化主要改善工具耗时，不能直接减少模型决策轮数。
- 隐藏卡片的替换、旧输出折叠和媒体保留策略仍可能改变缓存前缀。本次日志已有明显缓存命中，不能把问题描述为“没有缓存”。后续应记录每跳 prefix 变化位置、缓存 token 和首 token 延迟。
- 历史 FTS 的 `session_id/seq` 为 UNINDEXED 字段，逐条 upsert 的删除查询、全会话重建及兄弟会话文件读取还有可优化空间。本次中文和索引恢复 fallback 为有界词法匹配、线性扫描原事件，并未引入 embedding 服务。
- 现有 hyper-bench 主要是三类短编码任务，不能代表 20–50 轮连续会话。应固定长期约束和验收任务，测约束保持率、答案准确率、完成任务的模型轮数、无证据工具占比、重复验证次数、输入/缓存/输出 token、首 token 与总耗时。要优化“正确完成任务的总成本”，而不是单独压低工具数量。

新增离线回归覆盖：正常工具历史跨轮保留；中文早期要求检索；长事件命中窗口；跨压缩/重启且 SQLite 索引丢失的召回；Search 片段后的补充读取；编辑后的重新读取；同正则不同路径的 Grep；本地压缩清理旧快照；连续官方压缩后缀；编译双管道大输出与失败状态；中文诊断截断。在线模型表现和 Cursor 同题对照尚未测量。

验证结果：`cargo test --workspace` 共 1311 项通过、0 项失败、50 项按原有标记跳过（包括真实端点测试）；`git diff --check` 通过。统计脚本已在本机历史日志上运行，Python 语法检查通过。

源码修改需重新构建并启动新二进制后生效；本次没有终止现有会话或替换正在运行的程序。可用 `cargo build --release -p hyper-cli` 构建，然后在方便结束现有会话时用新二进制启动。
